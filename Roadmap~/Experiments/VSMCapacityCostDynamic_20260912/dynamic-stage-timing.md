## Fixed observation design

- All eight scenarios run forward, then the same eight in reverse: static, camera slide, camera turn, thin sweep, deform, receiver slide, receiver lift, sun rotate. There are 16 separate windows, named `<scenario>_adaptive_forward/reverse`.
- Every window explicitly enables VSM, SMRT, four maximum adaptive rays, spatial denoise and short temporal history. Effective layout must be 2048 resolution, 256 pages, 16 layers. Other shadow parameters inherit the scene and are saved in full. Receiver dimensions and effective SMRT/quality values must remain unchanged during each window.
- The trajectory uses the exact 32-frame quality pose formula, at its original movement speed. It repeats during **both** warming and observation. Each cycle includes the abrupt frame 31 to 0 reset. This is intentionally a repeated motion-and-reset workload; it is not a single slowed 128-frame trajectory or an uninterrupted smooth sweep.
- A single setup callback saves effective metadata/settings and is excluded. The next 64 consecutive selected-camera callbacks warm two cycles and exercise `Observe`; the recorder arrays are then reset. The next 128 callbacks observe four cycles. All 16 windows thus contain 2048 observations and 1024 warm callbacks, plus 16 setup callbacks. History is reset at each window boundary, and no BND `frame & 255` alignment is imposed.
- The production `beginCameraRendering` event applies the pose before GPU scene culling. The existing `CSMShadowResolvePass.EditorReceiverCapture` event calls `Observe` after the production resolve/filter commands have been recorded. Fixture transforms and deforming mesh data use the same paths as the quality harness.

## Work excluded from the observation path

The timing branch neither loads the reference compute shader nor creates the diagnostic RTAS, reference outputs or capacity buffers. It returns before reference dispatch, GPU readback, screenshot requests and per-frame JSON writes. It does not invoke a GPU drain on disposal. The ordinary render pipeline continues running normally; this statement concerns additional diagnostic work.

The plain Unity `MeshRenderer` fixture stays a scene caster (`HideInHierarchy`, without `DontSave`), using the cloned default Vivid material with `_Cull=0`, two-sided shadows and shadow receiving. Rigid fixtures retain `DynamicTransform`; the sheet retains `DynamicGeometryManualUpdate` and updates its vertices/normals/bounds. These ray modes match the quality fixture metadata; the timing harness itself builds no RTAS. The first callback verifies rendering-layer intersection and the production material compatibility predicate. Compatibility raster cost belongs to `VSM.UnityCompatibilityRaster`; these fixtures do not establish a moving-meshlet cost baseline.

`warm-start.json` and `settings.json` are written before the 64 warm callbacks. `window.json`, `settings-final.json` and `stage-timing.csv` are written after the 128 observations, before advancing the scenario. Metadata contains scenario/order, counts, first/last camera frame IDs, dimensions/layout, AA, effective quality and SMRT values, scene/fixture poses, caster material/mode/layers and final history validity. The original camera/light/settings are also archived. Camera/light transforms, transient volume/material/mesh/fixture and run-in-background state are restored on completion/cancel; assembly reload and Editor quit also dispose the probe. Neither scenes nor shared assets are saved.

## Interpretation and acceptance

`ProfilerRecorder` reports its last completed profiling frame. The camera IDs in CSV are observation timestamps, **not GPU frame identities**. Observations can repeat a completed result; 128 observations do not prove 128 distinct completed GPU frames. GPU completion lag prevents labeling a timing peak as the exact reset frame. The 32-frame workload repeats at the same speed, but its production BND phase is not paired with the quality capture. Keep these timing distributions separate from both the quality frame metrics and the earlier warm static timing experiment.

Before comparison require root status `complete`, exactly 16 windows with 128 rows of observations each, 64 consecutive warm IDs and 128 consecutive observed IDs per window, expected order/configuration, nonzero available samples, and valid final temporal history. Keep a missing/zero recorder sample visible rather than treating it as measured zero cost. Report forward/reverse medians and P95 separately before pooling. Compare exclusive parent stages; `ResolveTrace`/filters are children of `Resolve`, and `PageCull` can run inside both caster-cull parents, so do not sum overlapping markers. Analyze moving/camera/sun windows independently of `static` and report distributions rather than exact frame-to-GPU causation.
